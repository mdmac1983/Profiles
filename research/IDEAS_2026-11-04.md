# Ideas, experiments and plans (Tj's research requests, 2026-11-04) — evidence from emulator runs 52-55

Everything marked **MEASURED** was run on the CI emulator (Android 10 x86). Anything marked **UNVERIFIED** needs your tablet. Tablet facts I still lack are collected by `tools/adb-probe.sh`.

## 1. Keeping the two launchers separate, effective and fast

### What exists and is MEASURED
| Mechanism | Result |
| :- | :- |
| Close Quickstep's apps **at lock** through the adb helper (force-stop + remove Recents cards) | 11 apps stopped in 164 ms **before any wake**; Recents cards gone; custom account already active behind the lock screen; no black cover at unlock (run 52) |
| Switch the quick-settings tile list per launcher | SystemUI's own dump shows only the rotation tile in custom, Wi-Fi + rotation in Quickstep (the emulator has no Bluetooth hardware); an extra tile added in custom is removed again within seconds (run 52) |
| `pm suspend <pkg>` as the shell user | WORKS. The app's **Recents card disappears** and starting it shows Android's "app paused" screen; the **process stays alive** (same pid). BUT after `pm unsuspend` the Recents card did **not** come back. So it is a "hide + stop launching" switch, not a way to keep a card in Recents (run 54) |
| `pm hide <pkg>` | REFUSED: the shell user lacks MANAGE_USERS (run 54) |
| A real second Android user | Possible only if `pm get-max-users` > 1 (emulator: 4). The switch ends on the **other user's own lock screen** (screenshot 71): not seamless. The first user's app process stayed alive. Per-user apps, notifications and Recents are separate by design (run 53) |

**Conclusion for "each launcher keeps its own apps open, hidden from the other":** not possible seamlessly on one Android user (one Recents list, one shade, and every hiding trick either kills the card or needs a permission the shell user does not have). The design that is built (invisible close at lock, instant custom account at unlock) is the best seamless form; a real second user is the only true separation and is not seamless.

### Clever ideas worth doing (ranked)
1. **Self-adb: the launcher starts its own helper after every restart, no computer.** If the tablet keeps "ADB over network" on across restarts (probe: `service.adb.tcp.port`, `persist.adb.tcp.port`), the launcher can talk to adbd on 127.0.0.1 itself (it needs a small adb-protocol client and one "Allow" tap the first time). That removes the one chore (running the helper line after each restart). **UNVERIFIED, needs the probe.**
2. **Per-launcher settings bundles** written by the launcher on each switch (each default OFF, snapshot + restore like the tiles): Do-Not-Disturb level (`zen_mode`), animation scales, screen timeout, brightness, font scale. Cheap, safe, instant; makes the two sides feel like two accounts. (Settings names exist on the emulator: `zen_mode`, `navigation_mode`, ...; your tablet's list comes from the probe.)
3. **Per-launcher skin with pre-installed overlays** (`cmd overlay enable/disable`, shell user): the emulator lists 47 (navigation mode, icon shape, accent, font). Your tablet's list is in the probe; a different icon shape / accent colour per launcher would make them look like two different accounts. Optional, cosmetic.
4. **App-ops per profile** (`cmd appops set <pkg> RUN_IN_BACKGROUND deny` for Quickstep apps while custom is active): stops their background work without closing them. **UNVERIFIED**, small gain.
5. **Do-Not-Disturb policy** to hide the whole shade in custom: needs policy access (`cmd notification allow_dnd`) and a manifest change; hides all notifications (also custom's own). Low value now that apps are closed at lock.

## 2. Power menu: Power off + Restart only, no visible delay

Why there is a delay: the real menu is a window of SystemUI; the first thing the accessibility service can see is that window appearing (about 50-150 ms later), then our card is shown over the Screenshot slot. In every emulator run the log says "real menu not seen before the card": the card is up at the first event.

Ideas, tested or reasoned:
- **Early warning from the side key — DEAD (MEASURED).** An input monitor would see the key before the menu. The shell user is refused: "Requires MONITOR_INPUT permission" (run 54). The accessibility service never receives the side key (earlier result). Nothing earlier than the menu window exists.
- **Overlay (RRO) that edits `config_globalActionsList` — DEAD.** Third-party overlays cannot override that resource (signature/system overlayable policy) and the bootloader is locked.
- **A setting that hides Screenshot — NOT in stock Android 10** (the list is the resource above; no setting). **If your ROM is LineageOS** it has a power-menu setting (`power_menu_actions`): then `Screenshot` can be switched off with no overlay and no delay at all. The probe prints it (`adb shell settings get secure power_menu_actions` and the `lineagesettings` provider). **This is the best-case fix; please run the probe.**
- **Read the real list from your tablet.** `tools/adb-probe.sh --pull` copies `framework-res.apk`; the list (`config_globalActionsList`) and any vendor additions are then known exactly instead of guessed.
- **Keep the current card but make it earlier / invisible:** the card is pre-built; remaining latency is the event. Measured by the launcher itself on your tablet ("Speed of the last menu" in Launcher control). If it is under ~150 ms it is below what the eye catches on a wake-up animation.
- **Replace instead of cover:** a quick-settings tile / launcher icon "Power off" / "Restart" that calls the helper (`reboot`, `svc power shutdown` run as the shell user) and the side-key menu blocked in custom. Zero menu to hide. Costs the real menu in custom.

## 3. The pencil icon in the notification panel: no delay

- The pencil only edits tiles. In custom the **tile guard now puts the list back** within seconds, so a pencil edit can no longer change anything: it is cosmetic.
- Current cover: appears when the accessibility service has found the pencil node (needs a node scan after the panel opens). The scan cannot be skipped safely: the shade window exists full-screen even when collapsed, so "panel open" cannot be told from bounds alone; showing the cover on every SystemUI event would flash a white box over apps.
- **Native switch — MEASURED, WORKS on the emulator (run 55, screenshots 73 vs 74).** With `Settings.Global device_demo_mode = 1`, SystemUI's own quick-settings footer is drawn **without the pencil and without the gear** (the panel is otherwise identical: tile, brightness slider, page dots). Nothing is covered, so there is no delay at all. The power menu is unchanged in that mode (Power off / Restart / Screenshot / Emergency: screenshot 75), so it does not help the power menu. The launcher writes the flag only while the custom launcher is active (opt-in switch in Launcher control, default OFF, snapshot + restore like the tiles) and the pencil cover steps aside while it is on. UNVERIFIED on your tablet: demo mode is a retail-demo flag; the emulator showed no other change, and the lock screen is covered by an emulator check, but only the tablet can confirm. Try the one adb line in research/ADB_TODO.md (E1) first.
- Other ideas considered and rejected: status-bar disable flags (switch off the whole panel, not the pencil); overlays (not possible, see section 2).

## 4. The cloned Settings app — plan

### The hard limit (unchanged, from research/SETTINGS_CLONE_2026-11-02.md)
The real Settings app is a system app (shared uid, platform-signed, hundreds of signature permissions). A normal app cannot be a copy of it. What CAN be done is a **front door that looks stock and opens the REAL pages**, with the pages you do not want blocked. That is "functional" because the pages are the real ones.

### What you can send (in order of usefulness)
1. **Screenshots** of exactly what you want: the Settings home, plus every sub-page you want kept (one screenshot each), and a list of the rows to **remove / reorder / keep**.
2. **Probe output**: `bash tools/adb-probe.sh` (read-only) and, for the look, `bash tools/adb-probe.sh --pull` which copies **the tablet's own Settings APK** (and the framework). With the APK I can read the exact strings, row order, icons and the list of pages (`aapt2` / `apkanalyzer` are in the container; GitHub tools like jadx are blocked here, but they are not needed for resources).
3. **Which Settings pages must keep working** inside the custom launcher (Wi-Fi is switched off there, so probably Display, Sound, Battery, Storage, About, Date & time, ...).
4. Whether the tablet is **LineageOS** or the vendor build (the probe prints it): decides the source I compare against.

### Where the source is online
- **AOSP Settings, Android 10** (tag `android-10.0.0_r47`): reachable from this container (`android.googlesource.com`); already downloaded once on 2026-11-02 and measured (2,917 files). Good for the look: layouts, preference XML, icons (Apache-2.0).
- **LineageOS Settings** (`LineageOS/android_packages_apps_Settings`, branch `lineage-17.1`): GitHub is **blocked** from this container, so I cannot fetch it. The tablet's own APK is the substitute.
- **Extracting the code from the tablet:** the APK (resources and bytecode) can be pulled by you with adb; running it is impossible (system-signed), but reading it is enough to copy the look.

### Staged implementation plan
- **S0 inputs** (waiting on you): screenshots + probe/APK + keep/remove list.
- **S1 the front door:** a `SettingsHomeActivity` that looks like the stock home (search box, coloured circle icons, title + summary rows, exact paddings/fonts from the screenshots; 600x1024, 170 dpi, font scale 1.2 so the emulator comparison matches your tablet). Plain framework views, no library (Go memory).
- **S2 row routing:** each row opens the real page by its public Settings action (from the probe's `android.settings.*` list). The list lives in preferences, so you can hide/reorder rows in Launcher control (Quickstep only), like the app chooser.
- **S3 the guard** (accessibility, custom mode only): if a Settings page that is not on your allowed list opens (class names from the probe), send you back to the front door — same pattern as the stray-Quickstep guard, with the same fail-open rules. This is what makes "removed" settings really unreachable (Settings search and "Advanced" links included).
- **S4 gear + drawer:** the stock Settings icon is hidden from the custom drawer and replaced by this one; the gear in the notification panel opens it (touchable cover over the gear, needs your OK for a touchable overlay on the lock screen, as noted in the C4 research).
- **S5 proof:** emulator section for the routing and the guard; look check by pixel comparison against your screenshots; then a tablet test.
- Risks: a vendor page the guard does not know yet (fails open: the page just opens); an accessibility cost per window event (kept to Settings' package only).

## 5. The accelerometer for the way back (Quickstep -> custom) — answered

**Yes**, and it is built (v0.5.0): two more "back to custom" methods, **Triple shake** and **Double knock**, switchable in Launcher control, default OFF, labelled experimental. The accelerometer is read **only while Quickstep is active and the screen is on** (not in the custom launcher, not with the screen off). The thresholds are a first guess (shake = three jolts above 11 m/s2 within 2 s; knock = two small sharp jolts 0.15-0.7 s apart with quiet before and after; a finger tap and walking are ignored in the JVM tests); they cannot be tuned without the tablet, so tell me if it is too touchy or too stiff.

## 6. P2 — keep Quickstep's apps OPEN but invisible in the custom launcher? (re-research, Android 10 source r47, 2026-11-04) — answer: NOT seamlessly
Sources read: `NotificationShellCmd.java`, `NotificationManagerService.java`, `RecentTasks.java`, `TaskRecord.java` (android.googlesource.com, tag android-10.0.0_r47).
- **Notifications CAN be hidden without clearing them.** `cmd notification suspend_package <pkg>` (shell may run it; the source says "only use for testing") fires the package-suspended path, which calls `hideNotificationsForPackages`: every current notification of that package gets `setHidden(true)` and the shade stops listing it; `unsuspend_package` brings them back. LIMIT: it only simulates the broadcast; the package is not really suspended, so notifications the app posts AFTER the call are shown normally (the helper would have to repeat the call every few seconds, or a notification listener would have to notice new posts).
- **Recents cards and app screens CANNOT be hidden while kept open.** The real hide switch is `pm suspend`, and `RecentTasks.onPackagesSuspendedChanged` does `removeTaskByIdLocked(taskId, killProcess=false, REMOVE_FROM_RECENTS)` — it REMOVES the task and finishes its activities (the process stays alive, which matches the emulator result: same pid, card gone, not coming back after `pm unsuspend`). So the screens and their state are lost either way; only the process survives (background audio / downloads), and on a 1.3 GB tablet Android's low-memory killer will reap that cached process soon anyway.
- No shell-reachable switch exists to mark an EXISTING task "excluded from Recents" (`excludeFromRecents` is an Intent flag read when the task is created); `RecentTasks.mHiddenTasks` is internal to the window manager; `pm hide` needs MANAGE_USERS (refused). A second Android user is the only real separation and is not seamless (research section 1).
- Decision for Tj (standing wish: ideal IF seamless): not possible seamlessly. Possible half-measure if he wants it later: replace "force-stop" at lock/switch by "hide the notifications + remove the tasks without killing the process" (suspend then unsuspend at once). Gain: Quickstep apps' background work and a faster warm start survive; cost: they keep using RAM and posting notifications that must be re-hidden. NOT built; ask Tj only if he cares about background work surviving.
