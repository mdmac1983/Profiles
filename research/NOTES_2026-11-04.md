# Research notes, 2026-11-04 (Tj's C3-C7) — read with TASKS.md

## C4 — can the notification-panel gear (Settings) open our cloned Settings?  YES, with limits
- The gear is `com.android.systemui:id/settings_button` (QS footer, qs_footer_impl.xml). SystemUI starts the REAL Settings with an explicit intent, so we cannot "replace" the Settings app or intercept the intent.
- What works: the same accessibility-overlay trick as the pencil cover (B6): a small touch-capturing window over the gear; a tap starts OUR cloned Settings activity instead. Needs the helper ON and the cloned Settings to exist (SET1).
- Lock screen: the shade/gear is reachable there. A tap on our overlay would start our activity; Android shows the PIN bouncer first and then our clone (KeyguardManager.requestDismissKeyguard). Needs Tj's OK for a TOUCH-capturing overlay on the lock screen (so far only a non-touchable number and the power-menu cover are allowed there).
- Not possible: changing what the real Settings app contains, or hiding it from other entry points (Settings app icon, intents from other apps).

## C6 — separate notification panel / quick-settings tiles per launcher?  PARTLY
- Quick-settings tiles: YES. The tile list is the secure setting `sysui_qs_tiles`; SystemUI reloads it live. With WRITE_SECURE_SETTINGS (adb grant) the launcher can write e.g. `rotation` when the custom launcher becomes active and the full list again for Quickstep (snapshot + restore through RestoreStore, like the keyboard switch). Also: `icon_blacklist` (secure) hides status-bar icons per mode (battery + clock only).
- Lock-screen notification visibility per mode: secure settings `lock_screen_show_notifications`, `lock_screen_allow_private_notifications` (same grant).
- NOT possible: a different notification SHADE per launcher (its layout/contents belong to SystemUI). Hiding individual notifications per launcher would need notification access, which Android Go does not offer.
- Recommended build (needs the adb grant): tiles + status-bar icons per mode.

## C5 — "Launcher" and "Quickstep" never in Recents in ANY launcher
- Why Launcher showed: Android always lists the most recent task, even if excluded (RecentTasks.isInVisibleRange). Fixed by the HOME-type launch (v0.3.4, default ON).
- Why "Quickstep" can show: RouterActivity.startStock() starts the stock launcher with an EXPLICIT component, so Android makes an ordinary task of it (not HOME-type) and lists it. Fix: start it with an IMPLICIT HOME intent restricted to its package (setPackage(stock), no component) -> HOME-type, never listed. No adb needed.
- Control / chooser screens (label "Launcher control"): TaskDescription says "solitaire"; they only appear when opened from Quickstep.

## D7 — "two profiles of Android" (custom launcher = default, Quickstep only by gesture): options compared
Layers, cheapest/safest first:
1. DONE: router is the only Home; HOME-type custom launcher (never in Recents, Android resumes OUR home task); stray-Quickstep guard (accessibility presses Home); crash breaker.
2. NEXT (needs only the WRITE_SECURE_SETTINGS adb grant, survives reboots): per-mode SECURE SETTINGS written on every mode switch with a snapshot/restore: `sysui_qs_tiles` (tiles; the minimum-tiles rule is only in SystemUI's editor), `icon_blacklist` (status-bar icons), `lock_screen_show_notifications`, default keyboard (done), animation scales (done), `policy_control` (Android 10 only: hide status/navigation bar per mode).
3. DONE/ongoing: ACCESSIBILITY surfaces: pencil cover, power-menu card, lock-screen number, (planned) gear -> cloned Settings, selective Recents dismissal. Limits: reactive (a short flash is possible), needs the helper kept alive (battery whitelist), cannot copy the screen (Android 10 has no takeScreenshot for services).
4. OPTIONAL, needs adb once PER BOOT: a Shizuku-style shell-uid helper (or adb-over-TCP to localhost): the app can then run `am force-stop`, `pm grant` (it could grant itself every permission automatically), `cmd package set-home-activity`, `settings put`, `cmd statusbar`, `screencap`... Costs: a re-start by USB after every reboot (Android 10 has no wireless pairing) and a hand-written adb client or a dependency.
5. OPTIONAL, high risk: DEVICE OWNER via `dpm set-device-owner` (works on an already set-up device only with ONE user and NO accounts; plausible on a GApps-free LineageOS tablet). Gives LOCK TASK mode (disable Home/Recents/notifications/power menu/keyguard features per `setLockTaskFeatures`), `setPersistentPreferredActivity` (default home that a crash cannot clear), hide system apps. Needs a `testOnly` build so it can be removed with `dpm remove-active-admin`; a wrong policy can lock Tj out until adb. Not recommended without a tested escape hatch.
6. The REAL "two profiles": a SECOND ANDROID USER (or a restricted profile): separate default launcher, quick-settings tiles, notifications, Recents, keyboard, wallpaper, per user; switching goes through the lock screen (owner PIN = the "gesture"). Needs multi-user enabled on the tablet (`adb shell pm get-max-users` must print more than 1) and every app set up twice; user switch takes seconds on an MT8168. Worth checking with that one adb command before deciding.
7. NOT possible here: root, custom ROM/RRO overlays (locked bootloader), live screen mirroring (see D1).
Recommended path: 1 + 2 + 3 (+ selective Recents D5), then re-evaluate 6 (check max-users) and 4; keep 5 off unless Tj explicitly wants a kiosk.
