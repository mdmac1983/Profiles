# Two profiles: custom launcher = default account, Quickstep = the other account (Tj, 2026-11-04, N3)

Tj's spec: a plain PIN opens the **custom launcher** and locks the user into it; **Quickstep** only exists behind a secret handshake. The custom side
should behave like a separate user account (own Recents, notifications, tiles, radios, keyboard, power menu, boots into Solitaire) and "open like a regular unlock,
without any delay or closing apps or notifications".

## What Android 10 gives us, honestly

There is exactly **one** lock credential and **one** user, so no real account boundary exists unless a second Android user is created (option D below).
Everything else is a *profile switch* that we perform ourselves. The only moment the user does not see the screen is while the **lock screen is up**,
so the design does every switch there.

### What is built in v0.4.0 (needs only the Accessibility helper; no adb)

| Moment | What happens | Why it is invisible |
| :- | :- | :- |
| Tablet wakes to the lock screen | custom home + Solitaire are started **behind the keyguard** (Router extra `tj_prearm=custom`, then Solitaire once). `Mode` is left alone. | activities started behind the keyguard are hidden by it |
| Handshake accepted (before the PIN) | `Mode` flips to Quickstep (tiles / keyboard follow), the stock home is started behind the keyguard (`tj_prearm=stock`), 40 ms buzz | same |
| Enter tapped with a **plain** PIN while a Quickstep session is current | black cover goes up at once (`coverAtEnter`); it hides the unlock animation and the clean-up | the cover is a non-touchable accessibility overlay, removed when Solitaire is verified, after a wrong PIN, and by a 4.5 s failsafe |
| Unlock completes (USER_PRESENT), no handshake | session ends: `Mode` -> custom, return reset (kill Quickstep-opened apps, clear shade, Wi-Fi/BT off, Solitaire last) | under the cover |
| Unlock completes, handshake given | Quickstep home is already in front; pressed only if the pre-start did not land | nothing to hide |

A normal custom-to-custom unlock (the common case) therefore shows **Solitaire immediately, exactly like a regular unlock**: no cover, no closing, no clearing.
Only the *first plain unlock after a Quickstep session* has work to do (close the apps Quickstep opened, empty the shade), and that part sits under the black cover.

### Why that clean-up cannot be 100 % invisible without adb

Recents and the notification shade can only be emptied by driving their real UI ("Clear all"), and neither can be opened above the keyguard.
`killBackgroundProcesses` stops the processes but leaves the Recents cards. So that step needs the screen: it is hidden by the cover, not removed.
It is skipped entirely when there is nothing to do (no Quickstep app opened, no notification icon).

### Quickstep-opened apps never show in the custom launcher's Recents

* Custom launches carry `FLAG_ACTIVITY_EXCLUDE_FROM_RECENTS` except Solitaire (v0.3.0), the custom launcher itself is a HOME-type task and is never listed (v0.3.4).
* Quickstep-opened apps are tracked (`AppOrigin`) and removed from Recents by the return reset when the Quickstep session ends (selective per-card "Close", Clear all as fallback).
* Entry to Quickstep is now **only** the handshake and exit is only a lock (or double-Home); there is no gesture in the custom launcher any more.

## Safety valves (L10 says safety overrides everything)

* If the helper is **off**, no handshake can be seen, so three quick Home presses in the custom launcher switch to Quickstep (ignored while the helper is on).
* At least one handshake always stays on (all switches off => double erase stays on).
* The launcher crash breaker still falls back to Quickstep; while it is tripped, a plain unlock does **not** pull you back to custom.
* "Restore everything" switches the three profile switches off, so nothing of ours switches launchers any more.
* Stock Settings > Apps > Default apps > Home app always works as the outermost escape.

## The six handshakes (ideas not built: shake the tablet, knock twice on the back, rotate three times — each risks false positives or sensor battery cost and cannot be tuned without the tablet)

1. **Double erase**: Delete, Delete on the empty pad, then the PIN. 2. **Tap and erase**: digit+Delete three times. 3. **Volume code**: Up, Up, Down, Down in 6 s.
4. **Side-key flurry**: four screen changes in 4 s. 5. **Peek three times**: pull the pad up and away three times in 15 s. 6. **Volume Up + double erase**.
Digits are classified as "a digit key" only; the value is never read or stored. Volume keys are only seen on the lock screen, and only while method 3 or 6 is switched on.

## Ways BACK to the custom launcher (N4, besides double Home) — all switchable in Launcher control, all act only while Quickstep is active

| Method | How | Default |
| :- | :- | :- |
| Press Home twice | the original kill switch | always on |
| "Back to custom" icon | arrow icon in Quickstep's drawer (put it on the home screen if you like); never in the custom drawer | ON |
| Quick-settings tile | `custom(com.tj.launcher/.ReturnTile)`; add with the pencil (Quickstep has no pencil cover) or tick it in Launcher control > Quick settings | ON |
| Volume code | Down, Down, Up, Up within 6 s | ON |
| Three Backs + Volume Down | within 6 s | off |
| Both volume keys together | within 250 ms | off (grip risk) |
| Side-key flurry | 4 screen changes in 4 s | off |
| Lock the tablet | a plain PIN afterwards is the custom account | ON (Two profiles) |

Ideas not built: touch gestures in Quickstep (Quickstep owns its touches; an accessibility service sees none without touch-exploration mode, which would change how the whole tablet behaves).

## MASTER FAILSAFE: always reach Quickstep even if the lock-screen handshake never works (N5)

The lock-screen handshake can fail for reasons only the tablet shows (Lineage's keyguard may use other view ids than stock). So the failsafe ladder uses **different signals**:

1. Lock-screen handshakes (6 methods; `UnlockMethods`).
2. **Konami key code** anywhere in the custom launcher, screen unlocked: Volume Up, Up, Down, Down, Back, Back, Up, Down within 20 s. Uses the helper's key filter, not the keyguard. Default ON. Eight keys in order is not something a pocket or a child produces.
3. **Hidden Solitaire hotspot**: an invisible 56 dp square in a chosen corner, only while Solitaire is in front: 5 quick taps, then touch and hold ~1 s. Default OFF (it blocks that corner of the game); pick the corner in Control.
4. **Helper OFF**: three quick Home presses (router, needs no helper).
5. **Android itself**, needs nothing from us: Settings > Apps > Default apps > Home app > pick the stock launcher; Safe mode (hold Power off, long-press "Power off"; third-party launchers are disabled, stock Quickstep starts); `adb shell cmd package set-home-activity com.android.launcher3/<stock home activity>` (also in the adb guide).

### Card-move combination in Solitaire — answer
Solitaire is a third-party app; the helper can only read what the game exposes as accessibility nodes. Most card games draw cards on one canvas (nothing readable), so a card-move code is only possible if the game labels its cards ("7 of hearts"). Control > Master failsafe > **Probe Solitaire** runs a 10-minute probe: open Solitaire, move cards, return; it reports how many nodes carry text/description and samples. If cards are readable, the next step is a code such as "move a red 7 onto a black 8, then double-tap the ace of spades"; if not, the hotspot (a touch code in a corner) and the key code are the Solitaire-compatible secrets. Not decidable from here: the game is only on the tablet.

## Bigger options, ranked, for when Tj wants more separation

* **A. Shell-uid helper (Shizuku style), adb once per boot.** `am force-stop`, `cmd activity` task removal, `settings`, `pm grant` for itself: Recents cards of Quickstep apps removed
  *invisibly and instantly*, no cover needed. Cost: USB adb after every reboot (Android 10 has no wireless pairing) + a hand-written helper process. Best next step if the cover is not good enough.
* **B. Do-Not-Disturb policy (`cmd notification allow_dnd com.tj.launcher`, adb once).** The custom profile could run a policy that hides every notification from the shade, status bar and lock screen
  (`SUPPRESSED_EFFECT_*`), so "no notifications" would be true by construction instead of by clearing. Untested on Android Go; candidate experiment.
* **C. A real second Android user.** Own default launcher, tiles, Recents, notifications, keyboard, PIN. Needs `adb shell pm get-max-users` > 1 (Tj has not run it yet) and apps installed twice;
  switching takes seconds on an MT8168 and the user switcher is visible. The only true "account" separation.
* **D. Device owner / lock-task kiosk.** Strongest lock-in, risk of a hard lock-out; not recommended without a tested escape hatch.
