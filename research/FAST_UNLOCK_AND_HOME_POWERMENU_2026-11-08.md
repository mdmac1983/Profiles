## 0. The facts that bound everything (each with its source)

1. **Two kinds of means.** *App-only* (the accessibility service, overlay windows, settings writes with the adb grant) works on Tj's tablet today. *Helper-based* (the adb-started shell-uid process `ShellServer`: remove tasks by id, `screencap`, `getevent`, hold `DISABLE2_GLOBAL_ACTIONS`) does NOT work reliably there: HLP1 (open): the helper is gone a few minutes after it is started, cause unknown, and its output goes to /dev/null so a death left no trace; HLP2: the launcher cannot create TCP sockets (`EPERM`), only the abstract unix socket gets in; it dies at every reboot and needs the cable to start (`service.adb.tcp.port` is empty). TASKS AE1/AE4, RECENTS_AND_UNLOCK_AUDIT 2/7.
2. **The keyguard forbids Recents and the shade.** No on-screen clean-up can happen while the screen is off or locked (audit section 2). Task removal by id needs the shell uid.
3. **Accessibility cannot see the power key** (PWR2, `research/BUTTONMAPPER_2026-11-05.md`: `PhoneWindowManager` clears `PASS_TO_USER`, `AccessibilityInputFilter` skips such events). There is no early warning that the stock power menu is about to open; the earliest app-visible sign is the dialog's own window event, a few frames after its window was added.
4. **The stock dialog fades in.** `GlobalActionsDialog.show()` sets the container's alpha to 0 and animates it (and the scrim) over 300 ms with FAST_OUT_SLOW_IN: about 10 % opaque at 54 ms, 22 % at 72 ms, 35 % at 88 ms. A cover that is on screen within two or three frames of the window therefore hides a card that is still almost transparent. (Source: `research/AOSP10_BATTERYSAVER_AND_POWERMENU_2026-11-06.md`; the fade is `PatchFade`.)

## 1. BG1: the answers

| Tj's question | Answer | Since / status |
| :- | :- | :- |
| How much can be prepped invisibly while the lock screen is on? | The custom HOME is put in front behind the keyguard (activity created, process warm). With the helper running, Quickstep's apps and Recents cards are closed AT the lock, so the unlock has nothing to do. The patch window is created while the screen is dark. Without the helper the visible clean-up (shade, Recents) cannot be done while locked (fact 2) and needs the cover for as long as it takes. | pre-arm v0.7.3, lock-time clean-up v0.7.0 (helper), clean start + cover lifted the moment the home is in front v0.8.5 |
| Prepped as soon as the lock screen is on / the screen turns off? | Yes, both: `lockPrepare` runs at SCREEN_OFF + 0.7 s (and +6.5 s, and again at a locked wake) and does the pre-arm, the helper clean-up, the sweep and the patch window. | v0.7.3 / v0.8.5 |
| Start loading as soon as the user types a PIN with no gesture before it? | Nothing is left to START at that moment when the pre-arm worked: it already ran at screen off. The first digit would only help as a SELF-HEAL: if Android killed the launcher process while the tablet was locked, the custom stack is not in front any more and a cold start (1-3 s on this tablet) begins at the unlock instead of one or two seconds earlier. Because of fact 2 the first digit cannot start the visible clean-up either. Verdict: cheap, but only worth building if the new process-life record (below) shows the process really dies while locked. | not built; decision after the data |
| Can it be kept in RAM? | Three layers. (a) The accessibility service is bound by the system; that already lifts the process. (b) The optional keep-alive foreground service (Launcher control > Battery, radios & speed > "Keep the launcher in memory"): default OFF since v0.7.1 because Android refused its notification on Tj's tablet (crash loop); v0.7.2 fixed the icon and added a crash fuse, so it can be tried. (c) Launcher3 itself drops almost nothing when hidden (`Launcher.onTrimMemory` only releases a widget database cache; the service drops its wallpaper bitmaps only under REAL pressure). What nobody knows is how often the process is actually killed on the tablet: v0.8.7 records it (see section 3). | switch exists; measurement new |

## 2. BG1: ideas ranked (gain / risk), and what each needs

| # | Idea | Gain | Risk | Needs |
| :- | :- | :- | :- | :- |
| A | **Unlock path diet**: the accessibility service and the Launcher share ONE main thread; at an unlock the service did a `commit()` (fsync of the whole features file) and two to four file appends on that thread. Now `LockLog.add` is queued (in order) and the diagnostic commits are `apply()`. | small but certain (10-60 ms on eMMC) | none (nothing decides from the log) | built in v0.8.7 |
| B | **Measure before cutting**: process starts per day, oom_score_adj / importance at each lock, the helper's flight recorder (HLP1). | turns guesses into numbers | none | built in v0.8.7; Tj sends one tablet report |
| C | **Home-looking curtain instead of the black cover** (no-helper case, Quickstep -> custom): while shade and Recents are cleared behind the cover, show a picture of the custom home (rendered by the Launcher itself, so it can never contain a non-drawer app) instead of black, cross-fading to the real home. The unlock then READS as instant. Cost: touches on the curtain must be absorbed (or queued and replayed with `dispatchGesture`), the status-bar strip must be handled, one more overlay that can in theory outlive its purpose (the existing 4.5 s failsafe applies). | large in perception, zero in real time | medium (new overlay, touch handling) | Tj's yes/no; after the v0.8.5 timing numbers show the cover is still too long |
| D | **Persistent helper** (the real fix for "no cover ever", and for most of BG2): needs HLP1 solved. The recorder in v0.8.7 will say what kills it; candidates are a vendor cleaner, the low-memory killer, the adb session's cgroup. A self-restart after boot would need adb over TCP, which this ROM does not keep, and the launcher cannot open sockets (HLP2). | largest | n/a | ONE cable session (section 5) |
| E | First PIN digit as a self-heal of the pre-arm (see the table above). | rare cases | low | only if B shows kills while locked |
| F | Keep-alive on (existing switch). | avoids cold starts if the process is being killed | the earlier crash on this ROM (now fused) | Tj tries it; B shows whether it helped |

Not worth doing: pre-drawing the home "offscreen" (Android destroys the window surface while the activity is invisible; GPU textures are released on UI_HIDDEN, nothing app-side can prevent that), and `showWhenLocked` for the Launcher (it would show the home INSTEAD of the lock screen).
